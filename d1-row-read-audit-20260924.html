토브 D1 행 읽기 한도 조사

2026-09-24 KST · 운영 GraphQL D1 지표와 배포 소스의 읽기 전용 조사

결론: 무제한 폴러 호출의 증거는 없다. 관리자 조회의 반복 스캔이 계정 전체 무료 한도 500만 행/일을 넘겼다. 토브하우스 리드 처리 오류는 해당 계정의 D1 읽기가 막힌 결과다.

첫 한도 오류: Cloudflare D1 쿼리 기록에서 2026-09-23 16:00:13 UTC, 즉 2026-09-24 01:00:13 KST에 토브디자인 DB의 읽기 한도 오류를 확인했다. 토브하우스 DB와 토브디자인 DB 모두 01:00:14 KST에 같은 오류가 기록됐다. Telegram 알림 자체의 전송 시각은 별도 확인되지 않았다.

SQL별 수치는 Cloudflare D1 Query Insights 결과다. 일일 청구 지표와 집계 방식이 달라 SQL별 합계를 일일 총량과 동일시하지 않는다.

현재 보호 장치와 빈틈

  • 이번 비용 경로는 Airtable 호출이 아니다. 관리자 API는 D1을 조회한다. 남아 있는 airtable_id는 이전 링크 호환용 필드이며, 일부 Airtable 문구는 오래된 주석이다.
  • Meta 폴러는 0 * * * *로 매시 한 번 실행된다. 무제한 cron은 아니다.
  • 관리자 화면의 일반 접수 목록은 10건씩 요청하지만, 서버 API는 페이징 인자가 없으면 LIMIT 없이 전량 조회한다. 큰 OFFSET도 서버에서 제한하지 않는다.
  • 기존 leads(phone) 및 leads(createdAt) 인덱스는 연락처 REPLACE와 ORDER BY datetime(createdAt) 형태를 충분히 보호하지 못한다.
  • stats=1은 서버 TTL 캐시 없이 전체 집계를 다시 실행한다. 관리자 대시보드와 접수 탭에서 호출된다.
  • LIMIT은 반환량 상한이며, 이 쿼리들의 스캔량 상한은 아니다.

복구 위험과 조치

무료 한도는 UTC 자정, 한국시간 오전 9시에 초기화된다. 현재 한도 상태에서는 실패한 리드가 D1에 저장됐는지 확인하지 못했다. 토브하우스 폴러의 재조회 겹침은 6시간이므로, 한도 초기화까지의 시간이 이를 넘으면 자동 재처리가 보장되지 않는다. 초기화 후 해당 Meta 리드 ID의 D1 존재 여부를 읽기 전용으로 확인하고, 누락 시 중복 방지 키를 이용해 한 건만 복구해야 한다.

두 관리자 API의 상관 쿼리를 단일 집계로 바꾸고, 접수 목록에 커서 페이지네이션과 최대 100건 제한을 적용했다. 통계는 서버와 관리자 화면에서 2분 동안 재사용하고 상태 변경·삭제 시 즉시 비운다. 토브하우스 폴러는 한도 오류 때 처리 위치를 유지하고, 복구 뒤 24시간 범위를 다시 확인하도록 배포했다. 운영 DB의 새 인덱스는 사용자 요청대로 9월 25일에 적용한다.

배포 확인: 토브디자인·토브하우스 관리자 운영 Vercel은 모두 READY이며 공개 운영 주소에서 새 화면 코드가 확인됐다. 토브하우스 Worker도 새 버전과 매시 정각 cron이 확인됐다. D1 한도가 현재 막혀 있어 운영 DB에서 실패 리드의 저장 여부나 실제 읽기 절감량은 아직 확인하지 못했다.

예상 절감과 내일 확인

같은 사용량이면 읽은 행은 약 600만 행에서 200만 행 안팎 이하로 줄 것으로 예상한다. 이는 문제 SQL의 인사이트에 근거한 대략치이며, 인덱스의 추가 절감량이나 최종 사용량은 운영 적용 후 측정해야 한다. API 호출 횟수 자체는 크게 변하지 않을 수 있다. 두 DB 인덱스 적용, 실패 리드 저장 여부와 중복 알림 확인, 다음 24시간 rows_read 비교는 9월 25일 세션 핸드오프에 기록했다.
